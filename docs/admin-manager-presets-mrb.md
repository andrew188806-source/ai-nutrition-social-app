# ADMIN-MRB — 經理級權限模板（本地實作）

ADMIN-MRB V1 adds six versioned application presets to `/admin/management/staff/[staffAccountId]`. The manifest in `apps/admin-web/auth/admin-manager-presets.ts` is the exact source of preset IDs, labels, ordered CURRENT permission keys, and reason codes. A preset is a UI template over individual permissions. It is not a PostgreSQL role, wildcard, umbrella entitlement, database bundle assignment, or a replacement for the existing eight-key Primary Wizard. `admin.management.staff.bundle.write` stays PLANNED; no migration or new grant authority is introduced.

The page reads the target's current entitlements and the non-deferred live permission catalogue through the existing P3I read RPCs. It previews **Already held**, **Will grant via P3F**, **Will satisfy via P3E**, and **Unavailable / prerequisite required**. Apply requires the exact `APPLY <preset_id> TO <staff_account_id>` phrase, an active fresh TOTP Step-Up receipt, and the existing actor permissions. Each missing P3F-eligible key is sent individually through the existing `grant_privileged_permission` mutation path with a separate request ID and deterministic reason code. The backend still enforces P3F self-target denial, catalogue eligibility, actor permission-write authority, P3H receipt validation, and per-permission audit. A valid receipt may serve the sequence only during its existing window. The UI re-reads authority after each successful grant, stops on the first rejection, displays the successful audited prefix and failed key, and safely resumes from a fresh diff on retry. It does not roll back valid grants or automatically revoke a preset; the existing individual revoke control remains canonical.

`admin_context.read` is never sent to P3F. When missing and the actor has `admin.management.staff.console_admission.write`, Apply uses the existing `grant_console_admission` P3E mutation first, then re-reads target authority before P3F grants. Without that actor authority it remains a blocked prerequisite. `admin_restaurant_branch.status.write` is also never sent to P3F: the catalogue marks it ordinary-supervisor-delegable, so P3F rejects it. The two presets containing it (`highest_management_operational_v1` and `restaurant_operations_manager_v1`) remain blocked in full when it is missing. It must first be granted through its existing canonical ordinary path; after a fresh read sees it effective, the rest of the preset can proceed. No new ordinary grant API or database lane was added.

`highest_management_operational_v1` is an operational companion for an already-established Primary. A target lacking the existing eight Primary keys cannot apply it. V1 social safety covers only the CURRENT Social Policies permission; planned Social reports, deferred Nutrition modules, Business Development, and other future keys remain unavailable. Read-only managers may inspect the preview if their existing P3I read permissions allow it, but cannot apply without P3F permission-write authority. The backend does not trust UI visibility for authorization. No Break-glass, console admission, Primary, AAL2, or audit invariant is weakened.

Phase order after this mini-phase: **ADMIN-MRB → Group Table Inventory / 多人餐桌可回收性檢查 → Global QA / Integration / Handoff**. Group Table Inventory and implementation are outside ADMIN-MRB. Production, Development, and the fixed Demos are untouched by this local phase; Development live acceptance of the new flow remains separate.
