# 004 MVP Scope Summary

> Repository Status: Haocu OS Master Repository v2.0 Alpha 8.  
> Purpose: Clean investor / advisor / accelerator / restaurant-partner data room.  
> Boundary: External-readable summary only. Not legal, tax, accounting, securities, nutrition, medical, patent, privacy, or investment advice. Sensitive internal drafts and unreviewed details are intentionally excluded.

## MVP Goal

The MVP should prove that users can repeatedly complete the core Haocu loop:

**analyze or record meal → correct result → save meal → receive useful next-meal recommendation → optionally create a Meal Buddy/social action.**

The goal is not to prove every long-term business line at once. The MVP must be stable enough to demonstrate, pilot, and gather data.

## MVP-In Scope

| Area | MVP Scope |
|---|---|
| Mobile app | Login/demo access, AI analysis flow, correction, meal diary, today intake, recommendation, Meal Buddy, group table preview, chat/invite basics, profile/Premium limits. |
| AI | Food recognition assistance, nutrition estimation, candidate options, user correction, database-first lookup where structured data exists, cost/quality monitoring concept. |
| Data | User profile, meal record, AI analysis, correction, restaurant/menu, social card, match, chat/invite, table, analytics events, consent/audit primitives. |
| Restaurant | Restaurant cards, dish/menu data concept, dish-based social action, partner intake summary, admin review path. |
| Premium | Free/Premium capability limits, identity unlock concept, memory depth, candidate count, card limits. |
| Compliance | Privacy/terms draft boundary, health/nutrition disclaimer, consent points, social safety handling, sponsorship/partner disclosure rules. |
| Engineering | Build backlog, sprint plan, QA plan, technical risk register, demo seed/data strategy. |

## MVP-Out Of Scope / Later

| Later Area | Reason To Defer |
|---|---|
| Full medical nutrition coaching | Requires deeper regulatory, professional, and safety review. |
| Automatic clinical diet planning | Outside MVP and could create health-claim risk. |
| Full-scale restaurant analytics dashboard | Requires partner data and adoption evidence first. |
| Supply-chain / surplus food ESG system | Future Phase 2, not required to validate consumer loop. |
| Household nutrition planning / community fridge | Future Phase 3. |
| Complex multi-photo meal capture UI | Data model can prepare for it, but UI can be deferred. |
| Broad international expansion | Taiwan-first launch should validate local behavior first. |

## MVP Success Questions

The MVP should answer:

1. Do users understand the meal analysis and correction flow?
2. Do users trust the saved meal record after correction?
3. Do users find next-meal recommendations useful enough to return?
4. Does private taste/nutrition memory feel valuable?
5. Does optional Meal Buddy create engagement without overwhelming safety or moderation?
6. Are restaurants willing to provide structured menu/dish data or participate in pilot discovery?
7. Is there evidence that Premium or crowdfunding support can convert?

## MVP Evidence To Collect

- demo completion rate
- analysis correction rate
- saved meal count per user
- return usage after first saved meal
- next-meal recommendation click/save/action rate
- Meal Buddy card creation rate
- invitation/chat/table usage
- restaurant pilot interest
- Premium/crowdfunding willingness-to-pay signal
- qualitative user interview notes

## MVP Discipline

If a feature does not help prove the core loop, restaurant data fit, safety/compliance readiness, or monetization signal, it should be staged after MVP unless needed for a demo or review requirement.
